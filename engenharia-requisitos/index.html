Do Requisito Engessado ao Requisito Vivo

Esta aula compara dois jeitos de descobrir e documentar o que um software precisa fazer: o caminho clássico, criado por Ian Sommerville, e o caminho ágil/moderno, usado hoje na maioria das empresas de tecnologia.

Pense em Engenharia de Requisitos como a ponte entre o problema do mundo real e a solução digital. De um lado está a dor do cliente (o problema); do outro, o código (a solução). O requisito é o que garante que a ponte liga os dois lados certos — e não uma ponte bonita que termina no lugar errado.

Por que isso importa?

Existe uma regra de ouro nesta disciplina: um requisito não descreve "como" programar, e sim "o que" deve ser feito e "por que". Confundir essas duas coisas é a raiz da maioria dos projetos de software que dão errado.

O que você vai aprender nesta aula:
  1. Como funcionava (e ainda funciona, em alguns contextos) o processo tradicional de requisitos.
  2. Por que esse modelo quebra em um mundo que muda rápido.
  3. Como o Ágil resolve, passo a passo, cada uma dessas quebras.
  4. As ferramentas e técnicas modernas: User Stories, BDD, prototipagem, rastreabilidade automatizada.
Fundamentos

O que é um Requisito?

Antes de comparar os dois modelos, precisamos de uma base sólida: o que exatamente é um requisito? A disciplina define isso sob três ângulos complementares.

ÂnguloDefinição
A visão do usuárioUma capacidade necessária para resolver uma dor ou alcançar um objetivo.
A visão do sistemaUma condição que o software deve satisfazer para cumprir um contrato ou padrão.
O propósito (a ponte)É a ligação entre o problema real e a solução digital — não é sobre "como" programar, é sobre "o que" fazer e "por que".
Regra de ouro: um requisito bem escrito nunca dita a solução técnica. Ele descreve a necessidade. "O sistema deve validar o CPF do usuário" é requisito; "usar regex X para validar o CPF" já é decisão de implementação.

O clássico problema do balanço

Esta é a charge mais famosa da Engenharia de Requisitos, e ela resume o problema de comunicação em um projeto: cada pessoa envolvida entende o pedido do cliente de um jeito diferente — o cliente explicou um balanço simples de pneu, o líder de projeto entendeu outra coisa, o analista projetou algo mais elaborado, o programador construiu algo torto e caro, o consultor de negócios "vendeu" uma poltrona, o cliente foi cobrado por uma montanha-russa cara demais... e o que ele realmente queria era só um balanço de pneu num pneu velho.

As quatro causas raiz desse problema:
  • Falha de Comunicação — o que o cliente diz nem sempre é o que ele precisa.
  • Silos Departamentais — cada área (vendas, análise, desenvolvimento) interpreta o projeto sob sua própria ótica.
  • Falta de Validação — o usuário real só vê o produto no final, quando já é tarde demais.
  • A Ilusão do Óbvio — o que é óbvio para o desenvolvedor não é óbvio para o cliente.

O gráfico de custo: por que corrigir cedo é mais barato

Existe uma progressão de custo bem conhecida em engenharia de software, dividida em quatro fases:

Fase de Requisitos
Custo 1x
→
Fase de Implementação
Custo 10x
→
Fase de Produção
Custo 100x

Errar na fase de requisitos custa apenas papel e tempo de reunião. Mudar o código no meio do caminho exige refatoração (10x mais caro). Corrigir um bug com o sistema já no ar gera prejuízo real e estresse (100x mais caro). Por isso o objetivo moderno é "achatar a curva": descobrir o erro o mais cedo possível.

É como um erro de digitação: corrigir uma palavra errada enquanto você ainda está escrevendo o rascunho custa dois segundos. Descobrir o mesmo erro depois que o livro já foi impresso e distribuído em milhares de livrarias custa uma fortuna.
O jeito clássico (Sommerville)

Processo Clássico de Requisitos

O modelo tradicional, descrito por Sommerville, segue um fluxo linear e sequencial — cada etapa só começa depois que a anterior termina. Ele parte de uma pressuposição arriscada: prever 100% do sistema antes de escrever qualquer código.

Aprovação Formal

Depois de validado, existe ainda uma quinta etapa contínua: a Gestão de Mudança, responsável por controlar qualquer alteração nesse documento já "fechado".

1. Elicitação Tradicional

  • Foco em "Levantamento" — como se os requisitos já existissem prontos, bastando pegá-los do cliente.
  • Uso excessivo de entrevistas longas e questionários engessados (às vezes com 50 páginas), focados em "o que o sistema tem que ter?".
  • O analista atua como um "tirador de pedidos", apenas anotando o que ouve.
  • O grande erro: clientes geralmente não sabem o que querem até verem o sistema funcionando.

2. Análise e 3. Especificação (BDUF)

BDUF significa Big Design Up Front: tentar desenhar toda a arquitetura e os fluxos do sistema antecipadamente, antes de escrever a primeira linha de código.

CaracterísticaO que significa na prática
Documentos massivosConformidade com normas pesadas, como a Norma IEEE 830.
Casos de uso textuaisNarrativas longas e difíceis de entender para pessoas não-técnicas.
Contrato de proteçãoO documento vira um "escudo": se der errado, a culpa é de quem assinou.

4. Validação

  • O "Sign-off": a assinatura física ou digital validando centenas de páginas que o cliente mal leu.
  • Falsa Segurança: essa assinatura passa uma sensação de segurança para a equipe de TI que não corresponde à realidade.
  • O Gap de Imaginação: o cliente aprova um documento de texto, mas a mente dele imaginou uma tela completamente diferente da que será construída.

5. Gestão de Mudança

  • Conceito de mudança: mudanças são vistas como atrasos, aumento de custo e falhas de planejamento — não como algo natural.
  • O Comitê (CCB — Comitê de Controle de Mudança): um grupo formal criado justamente para dificultar a alteração de escopo.
  • Impacto burocrático: processo frustrante para o cliente, que vê seu negócio mudar enquanto o software fica obsoleto antes mesmo de nascer.
Resumo visual do processo clássico:
  1. Elicitação — questionários de 50 páginas focados em "o que o sistema tem que ter?".
  2. Análise e Especificação (BDUF) — Big Design Up Front, especificações IEEE 830, o grande "contrato" inflexível.
  3. Validação — o "sign-off": o cliente assina o documento "com sangue"; o código só começa depois disso.
  4. Gestão de Mudança — Comitê de Controle (CCB): mudar um requisito era julgado e punido como uma "falha".
Diagnóstico

Onde o Modelo Tradicional Falha

"O mundo real é dinâmico; documentos impressos não são." Essa frase resume, em uma linha, por que o modelo clássico entra em crise em projetos modernos.

ProblemaExplicação
VelocidadeMercados e tecnologias mudam mais rápido do que a capacidade de escrever e revisar documentos gigantescos.
Incerteza do ClienteClientes raramente sabem o que realmente querem até verem a tela funcionando.
Burocracia InútilNinguém — nem o desenvolvedor, nem o cliente — lê especificações textuais de dezenas de páginas.
Cultura da CulpaA armadilha tradicional: "o usuário aprovou o documento na fase 1; se ele não gostou agora, a culpa é dele".
É como planejar uma viagem de carro imprimindo o trajeto exato, minuto a minuto, antes de sair de casa — sem considerar trânsito, obras ou um posto de gasolina fechado. O papel não se atualiza sozinho quando a realidade muda; só um GPS (algo vivo e recalculando em tempo real) resolve isso.

Batalha dos mindsets: um resumo comparativo

TradicionalModerno (Ágil)
Planejamento inicial pesado → Previsibilidade → Foco no Sistema.Adaptação contínua → Valor Rápido → Foco no Usuário.

Não existe "errado" absoluto. Há o modelo certo para o projeto certo — um foguete da NASA provavelmente ainda precisa de muita documentação formal; um aplicativo de startup, não.

A virada

O Manifesto Ágil e os Requisitos

O Manifesto Ágil não é sobre abandonar disciplina — é sobre trocar as prioridades. Para requisitos, isso se traduz em quatro valores:

Valor ÁgilO que significa para requisitos
Software FuncionandoSoftware em funcionamento vale mais que documentação abrangente.
Colaboração com o ClienteColaboração com o cliente vale mais que negociação de contratos.
Resposta a MudançasResponder a mudanças vale mais que seguir rigidamente um plano.
Nota sobre DocumentaçãoAtenção: isso não é o fim da documentação — é o fim da documentação inútil.
Cuidado com um mal-entendido comum: "Ágil" não significa "sem documentação" ou "sem planejamento". Significa documentar e planejar só o necessário, no momento certo, e manter tudo vivo e atualizável.
Técnica

Fatiamento de Requisitos

No Ágil, um requisito grande (chamado de Épico) é quebrado em partes menores e independentes. Isso permite que o valor seja entregue em semanas, não em anos.

Pense em um queijo grande inteiro: ninguém consome ele de uma vez. Você corta em fatias — cada fatia já pode ser servida (tem valor sozinha), mesmo que o queijo inteiro ainda não tenha sido todo cortado. Um Épico é o queijo inteiro; cada User Story é uma fatia que já entrega algo útil por si só.

Sommerville também se atualizou

  • Engenharia de Requisitos Contínua: deixou de ser a "Fase 1" isolada e passou a ser um fluxo ininterrupto ao longo de todo o projeto.
  • Ciclos Ágeis e Features: novas features exigem novos requisitos a cada ciclo (Sprint) — não tudo de uma vez no início.
  • Ferramentas Virtuais: ferramentas pesadas de modelagem deram lugar a quadros virtuais colaborativos, com foco em colaboração online.
Ponto de atenção

Onde fica o RNF (Não Funcional) no Ágil?

Um Requisito Não Funcional (RNF) descreve qualidades do sistema — performance, segurança, usabilidade — em vez de uma funcionalidade específica. A pergunta que fica é: como garantir performance e segurança sem voltar a escrever documentos de 100 páginas de arquitetura? Existem duas soluções complementares:

Opção 1 — Definition of Done (DoD)Opção 2 — Critério de Aceite específico (BDD)
Regra global para todas as stories. O RNF torna-se uma regra fixa do sistema, aplicada sempre.

Exemplo: nenhuma User Story é considerada "Pronta" se as consultas ao banco levarem mais de 2 segundos. 		Embutido na história específica. O RNF é um critério de aceitação dentro daquela User Story, escrito em formato Gherkin (Dado/Quando/Então).

Exemplo: DADO senha digitada, ENTÃO ela deve ser criptografada com Hash SHA-256 no banco.
A opção 1 (DoD) é como uma regra de segurança da casa que vale para todo mundo, sempre: "todo mundo tira o sapato antes de entrar" (regra global). A opção 2 (BDD) é como uma instrução específica de uma receita: "se for usar o forno, pré-aqueça a 180°C" (regra dentro daquela tarefa específica).
Ferramental

Rastreabilidade Moderna

Rastreabilidade é a capacidade de ligar um requisito à história, ao código e ao teste que o implementaram — de saber, a qualquer momento, de onde veio cada linha de código.

Do Passado: Matrizes ManuaisDo Presente: Sistemas Integrados
Matrizes de Excel gigantescas, processo manual propenso a erros, falta de visão sistêmica. Rastreabilidade sistêmica e automatizada, integração de ferramentas-chave, dados fluidos e em tempo real. Ferramentas: Jira + GitHub/GitLab.

Mudança de mentalidade

Da Elicitação ao Discovery

Elicitação (Tradicional)Discovery — Descoberta (Ágil)
Foco no Sistema.
Exemplo: "O sistema deve ter um botão de exportar PDF."		 Foco na Dor.
Exemplo: "Por que o usuário precisa exportar esse PDF? O que ele faz com o papel depois?"

O Discovery usa Design Thinking: empatia, ideação e investigação profunda do problema antes mesmo de pensar em qualquer tela.

É a diferença entre um garçom que só anota "o cliente pediu água" (elicitação) e um garçom que percebe que o cliente está com sede porque acabou de correr, e já sugere também um isotônico (discovery). O segundo entende a causa, não só o pedido.
Do documento à conversa

De Especificação para User Stories

No modelo clássico, o requisito virava um documento estático de dezenas de páginas. No Ágil, ele vira uma User Story, estruturada nos chamados 3 Cs:

CSignificadoDescrição
Card (Cartão)O resumoA história deve caber num post-it. É apenas um lembrete de que uma conversa precisa acontecer.
Conversation (Conversa)O detalhamentoOs detalhes não são escritos de antemão — eles são conversados entre PO (Product Owner), Devs e Cliente.
Confirmation (Confirmação)A validaçãoOs critérios de aceite que provam que a história foi concluída corretamente.
O Card é como o título de um post-it colado na geladeira ("comprar leite") — ele não te diz qual marca, qual quantidade ou por quê; isso vem da conversa que você tem na hora de decidir. A Confirmation é a lista de conferência na volta do mercado: "comprei o leite certo?".
Do documento ao visual

De Validação para Prototipagem

Em vez de validar um documento de texto (que gera o "Gap de Imaginação" visto anteriormente), o Ágil valida protótipos visuais e interativos.

Prototipagem de Baixa FidelidadePrototipagem de Alta Fidelidade
Papel e caneta, wireframes (ex: Balsamiq). Valida o fluxo rápido, sem se preocupar com estética. Protótipo clicável no Figma. Valida a interface e as regras de negócio antes mesmo de codificar.

Benefícios da validação visual

A validação visual elimina cerca de 90% das ambiguidades que um texto puro carregaria — porque duas pessoas raramente imaginam a mesma tela ao ler a mesma frase.

"Um protótipo vale mais que mil reuniões de alinhamento."
Aceitando a incerteza

Gestão de Mudança Ágil

Aceitação de MudançasBacklog do Produto (Lista Viva)Hierarquia de Detalhe
Requisitos podem mudar, mesmo no fim do desenvolvimento. Mudança é vantagem competitiva! Uma lista viva, ordenada e eternamente incompleta. Prioridade e escopo evoluem constantemente. Itens do topo do Backlog são detalhados; itens do fundo são apenas ideias vagas ainda.

Repare o contraste direto com o CCB tradicional: lá, mudar era "julgado e punido"; aqui, mudar é esperado e até celebrado, porque significa que o time está aprendendo com feedback real.

Juntando todas as peças anteriores, o processo ágil de requisitos forma um ciclo contínuo de 4 etapas, com feedback constante voltando para etapas anteriores (não é uma linha reta como no modelo clássico):

Setas pontilhadas de feedback e iteração conectam as etapas de volta às anteriores: o que se aprende na Prototipagem pode gerar novas Histórias; o que se aprende na Gestão de Mudança pode voltar direto para a Descoberta. É um ciclo, não uma linha de produção.

A solução técnica

BDD: Fechando o Gap Semântico

1. O Problema

O Gap Semântico é a distância de vocabulário entre quem fala de negócio e quem fala de código: o cliente fala de taxas e vendas; o programador fala de banco de dados e APIs. As duas pessoas usam palavras diferentes para o mesmo problema — e é aí que nascem os mal-entendidos.

2. A Solução: BDD

BDD significa Behavior-Driven Development (Desenvolvimento Guiado por Comportamento). Ele usa uma linguagem estruturada e semi-natural — chamada Gherkin — que tanto o cliente quanto o programador conseguem ler e entender, no formato Dado / Quando / Então (Given / When / Then):

# Exemplo de especificação em Gherkin
Funcionalidade: Login de usuário

Dado que o usuário está na tela de login
Quando ele digita e-mail e senha válidos
Então o sistema deve conceder acesso ao painel
O Gherkin é como uma receita de bolo escrita de um jeito que tanto o chef quanto um ajudante iniciante conseguem seguir: "se a massa estiver homogênea, então está pronta para assar". Não é código puro, mas também não é uma redação livre e ambígua — é uma estrutura fixa que qualquer pessoa consegue ler.
Por que isso importa: como o Gherkin é escrito em uma estrutura fixa, ele pode virar automaticamente um teste automatizado executável (com ferramentas como o Cucumber). O requisito deixa de ser só um texto — ele vira também a prova de que o sistema funciona.

Prática

Exercícios

Exercício 1. Você está desenvolvendo o software das Urnas Eletrônicas do Brasil (o mesmo "Quiz Mental" proposto em aula). Esse sistema tem exigências legais rígidas, precisa de altíssima confiabilidade e não pode mudar de comportamento no meio de uma eleição. Você usaria o modelo de requisitos Tradicional (assinado, engessado, documentado) ou Ágil (volátil, rápido, aberto a mudanças)? Justifique.

Resposta esperada: Para um sistema como a urna eletrônica, o modelo Tradicional é o mais indicado — pelo menos para os requisitos críticos de segurança e integridade do voto. O motivo é o contexto: há exigências legais fixas, auditorias obrigatórias, e o "custo de mudança" durante a operação (Fase de Produção) é altíssimo — não há espaço para "aprender com o erro depois", como em um app comum. Isso não significa abandonar completamente práticas ágeis (protótipos, testes automatizados em BDD ainda ajudam), mas o processo de validação e o sign-off formal fazem sentido aqui, porque previsibilidade e rastreabilidade legal importam mais do que velocidade de entrega. Esse é exatamente o ponto da aula: não existe modelo "certo" universal — existe o modelo certo para o projeto certo.

Exercício 2. Reescreva a User Story abaixo separando corretamente os "3 Cs" (Card, Conversation, Confirmation), e depois escreva um critério de aceite em formato Gherkin (Dado/Quando/Então) para ela:

"O sistema precisa permitir que o cliente exporte o extrato de compras em PDF."

Resposta esperada (exemplo):
  • Card: "Como cliente, quero exportar meu extrato de compras em PDF."
  • Conversation: aqui entra a parte que não se escreve de antemão — o PO, o time e o cliente conversam sobre detalhes como: em qual tela fica o botão de exportar? O PDF inclui todas as compras ou só de um período? Existe limite de tamanho de arquivo? Essa é a etapa de "Discovery": descobrir a dor por trás do pedido (por exemplo, o cliente precisa do PDF para prestar contas à contabilidade).
  • Confirmation (critério de aceite em Gherkin):
Dado que o cliente está na tela de extrato
Quando ele clica em "Exportar PDF"
Então o sistema deve gerar um arquivo PDF com todas as compras do período selecionado

O raciocínio central aqui é: a User Story sozinha (o Card) é apenas um lembrete curto; o valor real está na conversa que detalha o "porquê", e a confirmação garante que todos concordam sobre quando a tarefa está de fato pronta — evitando o "Gap de Imaginação" visto no modelo tradicional.

Fechamento

Resumo Final da Aula

  • Um requisito é a ponte entre o problema real do usuário e a solução digital — nunca deve prescrever "como" programar, só "o que" e "por que".
  • O modelo Tradicional (Sommerville) segue 5 etapas lineares: Elicitação → Análise/Especificação (BDUF) → Validação → Gestão de Mudança, com base na pressuposição de prever 100% do sistema antes do código.
  • Esse modelo falha porque o mundo real muda mais rápido do que documentos impressos conseguem acompanhar, gerando burocracia inútil e uma cultura de culpa.
  • O Manifesto Ágil reordena prioridades: software funcionando, colaboração com o cliente e resposta a mudanças — sem eliminar documentação, apenas cortando a documentação inútil.
  • Requisitos grandes (Épicos) são fatiados em User Stories menores, entregando valor em semanas.
  • Requisitos Não Funcionais no Ágil vivem como Definition of Done (regra global) ou como critério de aceite específico em BDD.
  • A Rastreabilidade Moderna conecta automaticamente Épico → História → Branch → Pull Request, usando ferramentas como Jira e GitHub/GitLab.
  • A elicitação tradicional (foco no sistema) deu lugar ao Discovery (foco na dor do usuário), usando Design Thinking.
  • Uma User Story é estruturada nos 3 Cs: Card (resumo), Conversation (detalhamento) e Confirmation (critério de aceite).
  • A validação por assinatura em documento deu lugar à prototipagem (baixa e alta fidelidade), eliminando cerca de 90% das ambiguidades.
  • A mudança de requisitos deixou de ser punida por um comitê e passou a ser aceita como vantagem competitiva, gerenciada por um Backlog vivo.
  • O Ciclo Moderno conecta Descoberta → Histórias → Prototipagem → Gestão de Mudança Ágil, com feedback constante entre as etapas.
  • O BDD (Gherkin: Dado/Quando/Então) fecha o Gap Semântico entre a linguagem de negócio e a linguagem de código, virando especificação executável.
  • O cinto de ferramentas mudou: de Word/IEEE 830 para Jira; de UML pesada para Miro/FigJam; de texto para Figma; de requisitos manuais para Cucumber/Gherkin.

A grande virada em uma frase

A Engenharia de Requisitos deixou de tentar prever o futuro em um documento fixo e passou a construir um processo vivo, capaz de aprender e se adaptar a cada ciclo — sem nunca perder de vista a pergunta central: qual é o problema real que estamos resolvendo, e para quem?
